## Overview

> **Update · 13 Aug 2026 — the demo is a login-free stand-in for a live walkthrough of all four roles.**
> `student/`, `instructor/`, `tenant_admin/` and `super_admin/` are **click-through pages built from real screenshots of the working app** (`wgu.teamjft.com`), generated by [`build_prototypes.py`](build_prototypes.py) from a per-persona `flow.json`. Transparent, percentage-positioned hotspots sit over the real controls and call `goToScreen()` to advance.
>
> Three things changed on 13 Aug 2026, all in response to the demo being unusable as a stand-in:
> - **The AI interaction loop is now included.** Earlier revisions had no screen showing a model-generated question or a graded answer, which is the reason the platform exists.
> - **Every persona is on one course** — STU101 inside course folder B002 — so switching roles follows the same course through student, instructor and admin views.
> - **Each screen fills the browser width and scrolls inside its own frame**, so a 1,080px dashboard and a 6,100px analytics rollup present as the same shape instead of resizing the page on every click.
>
> The earlier hand-built HTML mockups are **preserved, not deleted**, in [`_archive/`](_archive/) — unlinked from the landing page but reachable by direct URL. The persona / scenario / design-system sections further down describe those **archived mockups**, which remain the design spec for surfaces JFT has not built yet.

**SkillProof** is WGU's AI coaching and assessment platform: an AI generates an assessment question, grades a free-text answer against per-objective Learning Objectives, and coaches the learner on the gap. It is **course-agnostic** — the first JFT release was a Python coding coach (E010), and the demo in this repo runs on **STU101 · Time Management & Study Skills** to show that the same engine works on non-coding content.

This repo holds two things: the **live-app click-through demo** (the four persona folders) and the **medium-fidelity storyboard** that JFT (Jellyfish Technologies) builds against, now archived in [`_archive/`](_archive/). The persona / scenario / design-system sections further down describe the archived storyboard:

- **Sally** (Student) — the v1.2 MVP coaching loop. **JFT shipped this first.** ([`_archive/student/`](_archive/student/)) — **18 screens**
- **Charlie** (Instructor) — At-Risk Intervention dashboard. ([`_archive/instructor/`](_archive/instructor/)) — **5 screens**
- **Alice** (School Admin) — Course + Skill management portal: School Dashboard with Course cards + filter/sort/search, 5-step New Skill wizard with Course Number/Title combobox typeahead, drill-chain mirroring Instructor for diagnostic, 4-level Analytics (School / Course / Skill / Topic). Scope is **Courses + Skills only** — at-risk learner tracking is Instructor's domain; School Settings + cross-School ops are Super Admin's. ([`_archive/tenant_admin/`](_archive/tenant_admin/)) — **12 screens**
- **Bob** (Super Admin) — Cross-School governance, financial controls, security compliance, **access control** (role elevation + School Admin → Schools + Instructor → Skills + Skill ownership / deployment), data + integrations hub, **School Management** (per-School branding / thresholds / retention — moved from School Admin v4.114), FERPA-aligned Logs, plus the inherited Course → Skill → Learner drill and 5-level Analytics. ([`_archive/super_admin/`](_archive/super_admin/)) — **11 screens**
- Plus **LRPS Landing** at the storyboard root ([`/`](./)) — recreated WGU internal Learning Resource Provisioning System; the realistic entry point for all four personas. **(v4.59: promoted to root; the standalone `/lrps/` URL was retired.)**
- Plus **Help & Resources** ([help/](help/)) — shared self-service support surface linked from every admin portal's navbar. Video training (§16.4 #9.15) is **deferred**, not built — see [`help/README.md`](help/README.md).

**Platform-wide:** every *analyzable* data table carries a consistent control bar — **filter chips + search + sort + a unified "Export ▾" dropdown** (shared [`assets/table-controls.js`](assets/table-controls.js)), with export formats matched to the audience (**PDF / CSV** for people, **MD / JSON** for machines such as logs). Editors and pick-lists (Topics/LOs, model picker) carry no controls. Long analytics pages have a **sticky scroll-spy section nav**; status colors use one **heat scale** (red → amber → green) across heatmaps, score pills, badges, dots, and threshold/budget bars; and create / delete / remove flows confirm via **modals**.

Each persona has its own **secret LRPS deep link** in production and authenticates separately. They share the SkillProof Design System v1.2 chrome and the WGU FY26 brand so the suite reads as one cohesive product family.

> **Implementation notes (for JFT).** The School Admin, Instructor, and Super Admin scenarios are the design spec for surfaces JFT has not yet started building. Use this storyboard as the visual North Star for the **full SOW scope**. WGU expects JFT to deliver every binding requirement in the MSA, the SOW body, and Appendix A within the contracted engagement window. The first JFT release was an MVP slice (E010 Coding Coach in `student/`); subsequent releases close the rest of Appendix A across the School Admin, Instructor, and Super Admin portals. The SC-MVP scenarios deploy the existing Cicada coaching loop as-is; the surrounding platform (multi-LLM orchestration, admin portals, observability, exports, integrations, compliance surfaces) is net-new build work per Appendix A. WGU also runs independent accessibility testing against WCAG 2.2 AA in addition to JFT's own self-checks per §16.2 #7.3 (student-facing surfaces; admin surfaces follow standard usability per SOW §3 Assumptions), so plan for remediation cycles inside the engagement window.

**Live-app click-through demo: 32 screens · 39 hotspots · 4 personas** (Student 8 · Instructor 8 · School Admin 10 · Super Admin 6), all four on **STU101 / course B002**. Every screen fills the full browser width and scrolls **inside** its own frame, so a 1,080px dashboard and a 6,100px analytics rollup present as the same shape. Hotspots are real clickable regions measured off the live DOM, so a whole role can be walked without logging in. The meta-bar switches roles, which is the point: one link replaces signing into four accounts to show the product. *(The archived mockups in `_archive/` hold the prior 46-screen hand-built set.)*

**The AI interaction loop is included on both sides**, which is the reason the platform exists: the student diagnostic shows an AI-generated assessment prompt and the model's per-objective scoring, and the coaching task shows an AI coaching prompt and its evaluation table. The Instructor **Skill Preview** shows the same loop from the staff side — an AI-generated question against a staging Skill, and the model's evaluation of a submitted answer, marked "Preview only — no data is saved". School Admin step 3 of the New Skill wizard shows the model choice, fallback chain, and compiled system prompt, and the preview grades against exactly the Learning Objectives entered in step 2.

Captures and hotspots are generated by `skillproof-qa-tools/demo-capture.js` (captures at 1920 wide; every PNG's width is asserted at build time) and verified by `verify-demo.js`, which clicks every hotspot and confirms it lands on the screen it claims. `flow.json` is script output, so re-run the capture rather than hand-editing it.

**Notes**

- **Super Admin deliberately has no heatmap or per-learner score screens.** Those exist for that role, but the same views are already covered under School Admin and Instructor, so they are not duplicated here (Brady, 13 AUG 2026).
- **Bump `v` in each persona's flow.json whenever screenshots are re-captured.** It drives the `?v=` cache-buster on every `<img>`; re-capturing without bumping it leaves browsers serving the previous images, so a shipped fix can look like it never deployed.
- **Student surnames are masked**; first names and all staff names are left visible, per the 12 AUG 2026 decision.
- **STAGE test data and "test" labels are expected** and left as-is — this is a beta test tenant, not a cleanup target.
- **Observed app drift worth reporting to JFT:** the live New Skill wizard’s step counter is inconsistent — steps 1-3 read "STEP _n_ OF 3", then the review screen reads "STEP 4 OF 5". The archived storyboard specified a 5-step wizard, so the counter appears to be a partial migration.
- The Instructor Skill Preview runs against **`STU101-PREV · Weekly Planning Basics`**, a staging Skill created in B002 on 13 AUG 2026 for this purpose. Staging means students cannot launch it, and only staging Skills appear in the instructor Preview list.

## Design System

The storyboard implements the **SkillProof Design System v1.2**, a brand theme layer on top of [Paragon](https://github.com/openedx/paragon) (Open edX's open-source design system).

| Layer | Responsibility |
|:------|:--------------|
| **Paragon** | Component structure, accessibility, base CSS (`@openedx/paragon`) |
| **WGU Brand Tokens** | Color, typography, spacing overrides (`--pgn-*` CSS custom properties) |
| **SkillProof Product** | Page composition, content structure, learning interactions |

### Color Palette (WGU FY26 — Authoritative)

| Token | Hex | Role |
|:------|:----|:-----|
| Deep Navy | `#001730` | Primary dark background, navbar, headers |
| Dark Navy | `#002855` | Deep accent, logo gradient |
| Bright Blue | `#0070F0` | Primary actions, CTAs, links |
| Sky Blue | `#46B1EF` | Secondary blue, accents, progress |
| Ice Blue | `#EEF6F9` | Light surface backgrounds |
| Accent Red | `#C13232` | Error states, emphasis |
| Amber | `#FBAE40` | Warnings, section accents |

Where FY26 and SkillProof Figma tokens conflict, **FY26 takes precedence**.

#### Documented palette extensions (intentional; out of FY26 scope)

Two specialized UI domains use deliberately extended palettes for clarity and industry familiarity. **These are intentional and must NOT be expanded to other surfaces.** Implementers should keep these scoped to their declared domains:

| Domain | Tokens | Where used | Justification |
|:---|:---|:---|:---|
| **Code-block syntax highlighting** | GitHub-style: `--code-keyword: #ff7b72`, `--code-function: #79c0ff`, `--code-string: #a5d6ff`, `--code-bg: #0d1117`, `--code-border: #30363d` | `_archive/tenant_admin/index.html` (prompt preview); `_archive/student/index.html` (read-only Python code editors) | Industry-standard code coloring (matches GitHub / VS Code dark themes). FY26 navy/blue would be unreadable for code tokens. |
| **Heatmap gradient** (9-step) | `--heat-1` through `--heat-9` (red → green via amber midpoints) | `_archive/instructor/index.html` screen 3 (15-learner × 4-Topic class heatmap) | Sequential data visualization needs perceptually distinct steps; FY26 has no diverging-scale tokens. |

All other surfaces (navbars, cards, forms, alerts, badges, status pills) use canonical FY26 tokens only.

> These two extensions describe the **archived mockups’ own CSS**. The four live persona pages carry no app CSS at all — they are screenshots of the real app plus transparent hotspots — so whatever the live app renders is what the demo shows.

### Typography

- **Headings:** Sora Bold (H1 40, H2 32, H3 28, H4 24, H5 20)
- **Body:** Lato Regular 16px / 1.5 line-height
- **Code blocks:** Lato 14px on `#0d1117` for JSON/API consoles; SkillProof-palette syntax in light mode for student code blocks
- **Type scale:** strict 12 / 14 / 16 / 18 / 20 / 24 / 28 / 32 / 40 / 48 px

### Spacing

8-point grid throughout. All padding, margin, and gap values are multiples of 8px.

### Branding

- Real **WGU FY26 Corporation logos** in [`assets/`](assets/) (White, Full Color, Full Color Reverse)
- **WGU owl favicon** (rebuilt v4.170) — the owl mark from the official Full Color Reverse lockup, white on an **opaque** WGU Deep Navy `#001730` square, so it reads on both light and dark browser chrome. Every live page declares `favicon.ico` (16/32/48), `assets/wgu-owl-favicon.png` (512), and `assets/apple-touch-icon.png` (180). Generated by [`make_favicon.py`](make_favicon.py); the art is only cropped and scaled, never redrawn.
  - Each `.ico` frame is rendered at its own size with size-specific padding and stroke weight, because a straight downscale of an outline mark to 16px averages the hairlines into mid-grey mush. The `v4.46`-era `assets/wgu-favicon.png` it replaced was never a favicon at all — it was the 2000×910 **wordmark** in navy on transparency, which squashed into an illegible blob and disappeared entirely against a dark tab strip. ## How to use

### Online

The portal selector at [brady-wgu.github.io/SkillProof/](https://brady-wgu.github.io/SkillProof/) links to every surface. From there you can open any portal directly, or open LRPS first and click into a portal via its provider row.

### Offline

Clone the repo and open `index.html` in any modern browser. No build step, no server required (the screenshot pipeline is the only thing that needs a local HTTP server). Files are fully self-contained beyond Google Fonts (Sora + Lato + Material Icons Outlined).

### Regenerate the live demo

The demo is captured from the real app, so it needs four authenticated STAGE sessions. The scripts live in `C:\Users\brady.redfearn\Claude Projects\skillproof-qa-tools` — that is the **run directory**, because it holds `node_modules` and the four Chrome profiles carrying live WGU SSO sessions. The same scripts are versioned in the private `brady-browser-kit` repo: edit and run them in the run directory, then copy to the repo, never the reverse.

```bash
cd "C:\Users\brady.redfearn\Claude Projects\skillproof-qa-tools"

# 1. Authenticate. Opens the four Chrome windows, tiled and labelled by role in the tab
#    title, then polls until each completes WGU SSO. You sign in; the script never
#    touches the login form. Fixed CDP ports: student 9301, instructor 9302,
#    schooladmin 9303, superadmin 9304.
node demo-reauth.js student instructor schooladmin superadmin

# 2. PRECONDITION for the student flow: the diagnostic must be COMPLETE before capture,
#    because Diagnostic Results, Progress Map and coaching all depend on it. A capture
#    run leaves it mid-attempt, so re-run this before every student capture.
node demo-seed-diagnostic.js

# 3. Capture, one persona per invocation.
node demo-capture.js 9301 flow-student.json
node demo-capture.js 9302 flow-instructor.json
node demo-capture.js 9303 flow-schooladmin.json
node demo-capture.js 9304 flow-superadmin.json

# 4. BUMP `v` in each flow-*.json you re-captured (see Notes above), then build:
cd "C:\GitHub Projects\SkillProof" && python build_prototypes.py

# 5. Verify against a local server before pushing.
python -m http.server 8000
#    ...then from the run directory, in another terminal:
node verify-demo.js 0 http://127.0.0.1:8000 student      # repeat per persona
node verify-frame-width.js http://127.0.0.1:8000
```

**What the tooling guarantees.** `demo-capture.js` forces the viewport on every screen, asserts each output PNG is exactly the configured width, measures every hotspot off the live DOM in the same page state it captures, refuses to capture a screen still showing a loading skeleton, and fails loudly if a redaction selector matches nothing. `verify-demo.js` then clicks all 39 hotspots and confirms each lands on the screen it claims. `build_prototypes.py` aborts if any referenced PNG is missing or the wrong width.

**What the tooling does not catch.** A hotspot that navigates correctly but sits on the *wrong control*. `Open Heatmap` on both admin Course Detail screens is targeted by index (`nth=5`), so adding or removing a Skill in B002 can shift it while every automated check still passes. Re-derive that index by hand whenever the course's Skill set changes.

### Regenerate the archived mockup screenshots

`capture_screens.py` belongs to the archived hand-built mockups in `_archive/`, **not** to the live demo:

```bash
python -m http.server 8000      # from the repo root
python capture_screens.py       # in another terminal
```

## For developers (JFT)

This storyboard is a **medium-fidelity sample**, not production code or a pixel-perfect specification. It illustrates the general look and feel of SkillProof and its administrative surfaces on a desktop browser. Use it as a rough guide for the intended user experience — adapt as needed for the production implementation.

When implementing:

1. **Install Paragon** — `npm install @openedx/paragon`
2. **Apply WGU brand tokens** via the brand package override mechanism (`@wgu/skillproof-brand`)
3. **Use Paragon React components** — do not rebuild them. The storyboard's CSS class names (`.pgn__card`, `.btn-primary`, `.pgn__breadcrumb`, etc.) map directly to Paragon's component schema.
4. **Per-persona portals are separately authenticated surfaces** — each has its own LRPS deep link. School Admin, Instructor, and Super Admin should not be combined into a single SPA shell; the auth flow and RBAC scoping are role-bound.
5. **Zero-trust authorization** — the LRPS link does not grant authority. Effective role and scope are determined server-side after authentication.
6. **Multi-tenancy maps to WGU Schools** — each WGU School is provisioned as a separate tenant internally. The example storyboard uses School of Technology as Alice's default School; additional Schools can be created via the Super Admin's School Management surface.
7. The CSS custom properties in the portal HTML files (`--pgn-*`) map directly to the Paragon token schema.
8. Each archived persona mockup has its own README in [`_archive/<persona>/README.md`](_archive/) listing the patterns and components introduced for that surface.
